Vision & Strategic Context

From Data Products to Intelligent Data Products

Today, ECDH delivers 16 clinical data products as denormalized Snowflake views. Consumers query views like vw_visits, vw_diagnoses, and vw_medications using SQL. This serves the structured analytics use case well.

The next evolution is to add an AI layer on top of every data product. Each data product gets a dedicated AI agent that can answer natural-language questions against its domain. At the platform level, ECDH Analytical Data Intelligence (powered by Snowflake Intelligence) orchestrates across all product agents and internal operational agents to provide a unified conversational interface for leadership, analysts, and clinical operations.

General Data Product (SQL-only) vs. Intelligent Data Product (AI Agent + SQL) — same data products, added intelligence layer

Same Question, Two Experiences

A care management director wants to know: "How many ED visits did we have last month, and which facility had the highest volume?"

⌨️ General Data Product (SQL-Only)

The director must find a SQL-skilled analyst, explain the question, wait for the query to be written and run.

-- Analyst writes this SQL manually SELECT facility_name, COUNT(DISTINCT encounter_id) AS ed_visits FROM ECDH_DB.CONSUMPTION.VW_VISITS WHERE visit_class = 'emergency' AND admit_datetime >= DATEADD('month', -1, CURRENT_DATE()) GROUP BY facility_name ORDER BY ed_visits DESC;

⚠ Pain Points:
  • Director can't self-serve — depends on analyst
  • Must know table names, column names, filter values
  • No narrative explanation — just raw numbers
  • Follow-up questions require another SQL cycle
💬 Intelligent Data Product (AI Agent)

The director opens Snowflake Intelligence and types the question directly in plain English.

👤
How many ED visits did we have last month, and which facility had the highest volume?
✨
Last month there were 14,303 ED visits across all facilities.

Mercy General Hospital had the highest volume with 3,847 visits (26.9% of total), followed by St. Luke's Medical Center (3,212) and Memorial Regional (2,956).

📊 Mercy General's volume is 19.8% above the facility average of 2,861.

Behind the scenes:

① Cortex Agent routes to Visits Agent
② Cortex Analyst generates the same SQL automatically
③ Query executes against vw_visits
④ LLM synthesizes a narrative answer with insights
✅ What's Better:
  • Director self-serves — no SQL knowledge needed
  • Instant answer with context and percentages
  • Follow-up questions in the same chat session
  • Same data, same security (RBAC enforced)
Cross-Product Follow-Up (Intelligence Layer): The director then asks "What are the top diagnoses driving those ED visits at Mercy General?" — the Intelligence Layer automatically routes this to both the Visits Agent and Diagnoses Agent, joins results by encounter, and returns: "The top 3 ED diagnoses at Mercy General are Chest Pain (ICD-10 R07.9, 412 visits), Abdominal Pain (R10.9, 387 visits), and Shortness of Breath (R06.02, 298 visits)." This cross-product join would require a second, more complex SQL query in the traditional model.
The Vision: Every data product ships with two interfaces — (1) a SQL view for programmatic consumers, and (2) an AI agent for conversational consumers. The ECDH Intelligence layer sits above both, routing questions to the right agent and synthesizing cross-product answers.

ECDH Intelligence Layer — The Unified Orchestrator

ECDH Analytical Data Intelligence

The top-tier Intelligence Layer is what leadership and cross-functional analysts interact with. It is a single Snowflake Intelligence interface backed by a master Cortex Agent that knows how to route questions to the right Product Agent(s) or Internal Agent(s) and synthesize a unified answer.

Think of it this way: The Intelligence Layer is the "Snowflake Intelligence for ECDH." It is NOT a data product itself — it is an orchestration layer that sits on top of all data products and agents.

Intelligence Layer Components

ComponentImplementationPurpose
Question RouterLLM-based intent classifier within the Cortex AgentDetermines which Product Agent(s) and/or Internal Agent(s) to invoke.
Multi-Agent OrchestratorCortex Agent with tool definitions pointing to each Product AgentExecutes parallel or sequential calls to multiple agents. Handles cross-product join logic.
Response SynthesizerLLM post-processor within the Cortex AgentMerges result sets from multiple agents into a coherent narrative with data tables, charts, and insights.
Guardrails EngineSnowflake RBAC + Cortex GuardrailsEnforces PHI/PII policies, ensures RLS bitstring filtering, prevents queries that exceed the user's access scope.
Custom ToolsSnowflake stored procedures / Python UDFs exposed as agent toolsEmail reports, trigger Streamlit dashboards, publish to Slack, generate PDF summaries.

Semantic Model Design — The Agent's Business Knowledge

Semantic Models: How Agents Understand Data Products

Each Product Agent requires a Cortex Analyst Semantic Model (YAML file) that describes the data product's tables, columns, measures, dimensions, and relationships in business-friendly terms.

Semantic Model Structure

ComponentWhat It DefinesExample (Visits Product)
TablesSource views the agent can queryECDH_DB.CONSUMPTION.VW_VISITS
DimensionsCategorical fields for filtering and groupingfacility_name, visit_class, discharge_disposition
Time DimensionsDate/timestamp fields for temporal analysisadmit_datetime, discharge_datetime
MeasuresAggregatable numeric fieldslength_of_stay_days (AVG), visit_count (COUNT)
RelationshipsCross-product join keysecdp_source_id → Patient, encounter_id → Diagnoses
Verified QueriesPre-tested question-to-SQL examples"How many ED visits last month?" → SQL
Best Practice: The semantic model is what makes Cortex Analyst accurate. Invest heavily in (1) clear business descriptions for every column, (2) verified query examples covering common questions, and (3) explicit relationships between tables.

Example Semantic Model YAML (Visits Product)

name: visits_semantic_model description: "Encounter/visit data product - answers questions about patient visits, admissions, discharges, facility utilization, and visit patterns" tables: - name: vw_visits base_table: ECDH_DB.CONSUMPTION.VW_VISITS description: "Denormalized view of all patient encounters/visits" dimensions: - name: facility_name description: "Name of the healthcare facility where the visit occurred" synonyms: ["hospital", "facility", "location", "site"] - name: visit_class description: "Type of encounter: inpatient, outpatient, emergency, observation" synonyms: ["encounter type", "visit type", "class"] measures: - name: visit_count expr: "COUNT(DISTINCT encounter_id)" - name: avg_los expr: "AVG(length_of_stay_days)" verified_queries: - question: "How many ED visits last month?" sql: | SELECT COUNT(DISTINCT encounter_id) FROM vw_visits WHERE visit_class = 'emergency' AND admit_datetime >= DATEADD('month', -1, CURRENT_DATE())
Governance, RBAC & Guardrails

AI Governance Framework

AI agents inherit and extend the existing ECDH data governance model. Every query executed by an agent passes through the same RLS bitstring model, RBAC roles, and data classification rules that govern direct SQL access.

Governance Stack

LayerMechanismWhat It Controls
Snowflake RBACExisting role hierarchy + RLS bitstring modelWhich data products and rows a user (and their agent) can access. Agent inherits the user's session role.
Cortex GuardrailsSnowflake built-in Cortex guardrailsPrevents prompt injection, off-topic questions, and adversarial queries.
Semantic Model FiltersDefault filters in YAML semantic modelAuto-applies mandatory WHERE clauses to prevent full table scans and out-of-scope queries.
Agent Audit LogSnowflake query history + custom loggingEvery agent interaction is logged: user, question, generated SQL, results returned, latency.
Model CatalogSnowflake Model CatalogRegisters which LLM powers each agent, version tracking, performance evaluations, cost governance.
EvaluationsSnowflake Cortex EvaluationsAutomated accuracy testing of agent responses against known-good answers.
Critical Principle: An AI agent never escalates access. It operates within the user's existing RBAC scope. If a user cannot see behavioral health data via direct SQL, the agent cannot see it either. The agent is a natural language interface to existing access, not a backdoor around it.

Agent Testing — From Snowsight to Local Development

How Snowflake Intelligence Routes Your Questions

When you ask a question in the Snowsight Intelligence UI, a Cortex Agent acts as the orchestrator. It classifies your question, determines which tools to call (Cortex Analyst for structured data, Cortex Search for documents, or both), executes them, and synthesizes a response. Every component in this chain can be tested independently from your local system.

Figure 6: Every component in the Intelligence chain is independently testable from your local machine
Key Insight: Snowflake Intelligence (the chat UI in Snowsight) is the user-facing wrapper — it is only available in the Snowsight browser. However, the actual work is done by Cortex Agent, Cortex Analyst, and Cortex Search — all of which have programmatic APIs you can call from VS Code, Python, REST, or CLI. You can test every agent component locally; you just won't get the Snowsight chat bubble.
Test Agents from VS Code — Step-by-Step

Testing ECDH Agents from VS Code

The Snowflake Extension for VS Code lets you run SQL worksheets and Python scripts against your Snowflake account. You can call the exact same Cortex APIs that the Intelligence UI calls internally.

Step 1 — Setup VS Code

Install Snowflake Extension

VS Code → Extensions Marketplace → search Snowflake → Install the official Snowflake Extension for Visual Studio Code.

Configure Connection Profile

Click the Snowflake icon in the Activity Bar → Add Connection → enter account (<org>-<account>), username, and authenticator (externalbrowser for SSO). Set role to ECDH_ANALYST and warehouse to ECDH_WH.

Verify Connection

Open a new SQL file and run SELECT CURRENT_ROLE(), CURRENT_WAREHOUSE(), CURRENT_USER(); to confirm you're connected.

Step 2 — Test Cortex Analyst (Text-to-SQL Agent)

This is the core engine behind most Product Agents. It takes a natural language question + a semantic model YAML and generates SQL.

-- ═══════════════════════════════════════════════════════════════ -- TEST 1: Cortex Analyst — Ask the Visits Agent a question -- This is exactly what happens when you ask about visits in Snowsight -- ═══════════════════════════════════════════════════════════════ SELECT * FROM TABLE( SNOWFLAKE.CORTEX.ANALYST( model => '@ECDH_DB.CONSUMPTION.STAGE/visits_semantic.yaml', question => 'How many ED visits did we have last month by facility?' ) ); -- ═══════════════════════════════════════════════════════════════ -- TEST 2: Cortex Analyst — Ask the Diagnoses Agent -- ═══════════════════════════════════════════════════════════════ SELECT * FROM TABLE( SNOWFLAKE.CORTEX.ANALYST( model => '@ECDH_DB.CONSUMPTION.STAGE/diagnoses_semantic.yaml', question => 'What are the top 10 ICD-10 codes for inpatient encounters this quarter?' ) ); -- ═══════════════════════════════════════════════════════════════ -- TEST 3: Cortex Analyst — Ask the Medications Agent -- ═══════════════════════════════════════════════════════════════ SELECT * FROM TABLE( SNOWFLAKE.CORTEX.ANALYST( model => '@ECDH_DB.CONSUMPTION.STAGE/medications_semantic.yaml', question => 'Which drug classes are most frequently prescribed for diabetic patients?' ) ); -- The response includes: -- • Generated SQL (what the agent would run) -- • Query results (the actual data) -- • Confidence indicators

Step 3 — Test Cortex Search (Document Search Agent)

This is the engine behind the Clinical Documents Agent. It performs hybrid keyword + semantic search over CCD narratives and clinical notes.

-- ═══════════════════════════════════════════════════════════════ -- TEST 4: Cortex Search — Search clinical documents -- This is what the Clinical Documents Agent uses under the hood -- ═══════════════════════════════════════════════════════════════ SELECT SNOWFLAKE.CORTEX.SEARCH_PREVIEW( 'ECDH_DB.CONSUMPTION.ECDH_CLINICAL_DOCS_SEARCH', 'Find discharge summaries mentioning post-surgical complications for cardiac patients', {'columns': ['document_content', 'patient_id', 'document_type'], 'limit': 5} ) AS search_results; -- Alternative: Query the search service directly with filters SELECT SNOWFLAKE.CORTEX.SEARCH_PREVIEW( 'ECDH_DB.CONSUMPTION.ECDH_CLINICAL_DOCS_SEARCH', 'abnormal lactate levels in sepsis patients', {'columns': ['document_content', 'encounter_id'], 'limit': 10} ) AS search_results;

Step 4 — Test the Full Cortex Agent (Orchestrator)

This tests the exact same orchestrator that Snowflake Intelligence uses — it routes to Cortex Analyst, Cortex Search, or both, and synthesizes a response.

-- ═══════════════════════════════════════════════════════════════ -- TEST 5: Cortex Agent — The full orchestrator -- This is the SAME agent that Snowflake Intelligence calls -- It decides which tools to use and synthesizes the answer -- ═══════════════════════════════════════════════════════════════ SELECT SNOWFLAKE.CORTEX.COMPLETE( 'claude-3-5-sonnet', CONCAT( 'You are the ECDH Intelligence agent. Use the following context from our visits data to answer.\n\n', 'Context: ', ( SELECT ARRAY_AGG(OBJECT_CONSTRUCT( 'facility', facility_name, 'visit_class', visit_class, 'visit_count', cnt ))::VARCHAR FROM ( SELECT facility_name, visit_class, COUNT(*) AS cnt FROM ECDH_DB.CONSUMPTION.VW_VISITS WHERE admit_datetime >= DATEADD('month', -1, CURRENT_DATE()) GROUP BY 1, 2 ORDER BY cnt DESC LIMIT 20 ) ), '\n\nQuestion: How many ED visits last month? Which facility had the most?' ) ) AS agent_response; -- ═══════════════════════════════════════════════════════════════ -- TEST 6: Cortex Agent via SQL — Create and call a named agent -- Define the agent with tools, then invoke it with a question -- ═══════════════════════════════════════════════════════════════ CREATE OR REPLACE CORTEX AGENT ecdh_visits_agent LLM = 'claude-3-5-sonnet' TOOLS = ( ANALYST(SEMANTIC_MODEL => '@ECDH_DB.CONSUMPTION.STAGE/visits_semantic.yaml') ) DESCRIPTION = 'ECDH Visits Agent — answers questions about patient encounters, admissions, ED visits, LOS'; -- Call the agent SELECT SNOWFLAKE.CORTEX.AGENT( 'ecdh_visits_agent', 'How many ED visits did we have last month by facility?' ) AS response; -- ═══════════════════════════════════════════════════════════════ -- TEST 7: Multi-tool Cortex Agent — Analyst + Search combined -- This mimics the Intelligence layer routing to BOTH tools -- ═══════════════════════════════════════════════════════════════ CREATE OR REPLACE CORTEX AGENT ecdh_intelligence_agent LLM = 'claude-3-5-sonnet' TOOLS = ( ANALYST(SEMANTIC_MODEL => '@ECDH_DB.CONSUMPTION.STAGE/visits_semantic.yaml'), ANALYST(SEMANTIC_MODEL => '@ECDH_DB.CONSUMPTION.STAGE/diagnoses_semantic.yaml'), SEARCH(SERVICE => ECDH_DB.CONSUMPTION.ECDH_CLINICAL_DOCS_SEARCH) ) DESCRIPTION = 'ECDH Intelligence — routes across visits, diagnoses, and clinical documents'; -- Ask a cross-product question — agent will choose which tools to call SELECT SNOWFLAKE.CORTEX.AGENT( 'ecdh_intelligence_agent', 'What are the top readmission diagnoses at our highest-volume ED facilities?' ) AS response;
This is your local equivalent of Snowflake Intelligence. Tests 6 and 7 create CORTEX AGENT objects with tool bindings (Analyst + Search). When you ask a question, the agent decides which tools to call — exactly like the Snowsight chat UI does. The only difference is you see raw JSON output instead of the pretty Snowsight chat bubble.
Test Agents from Python (Local System)

Python SDK — Full Agent Testing from Your Machine

Use the snowflake-ml-python SDK to test agents from any Python environment — VS Code terminal, Jupyter, or a standalone script. This gives you the most control for debugging, logging, and iterating on semantic models.

# ═══════════════════════════════════════════════════════════════ # TEST ECDH AGENTS FROM LOCAL PYTHON # Run this in VS Code terminal or any Python environment # ═══════════════════════════════════════════════════════════════ # pip install snowflake-ml-python snowflake-connector-python from snowflake.snowpark import Session from snowflake.cortex import Complete, CortexAnalyst, CortexSearchService # ── Connect to Snowflake (SSO opens browser once) ────────── session = Session.builder.configs({ "account": "<org>-<account>", "user": "<your_user>", "authenticator": "externalbrowser", "role": "ECDH_ANALYST", "warehouse": "ECDH_WH", "database": "ECDH_DB", }).create() # ── TEST A: Cortex Analyst (Visits Agent) ────────────────── print("=== Testing Visits Agent ===") response = CortexAnalyst.ask( session, semantic_model="@ECDH_DB.CONSUMPTION.STAGE/visits_semantic.yaml", question="How many ED visits last month by facility?" ) print("Generated SQL:", response.sql) print("Results:") print(response.results.to_pandas()) # ── TEST B: Cortex Analyst (Diagnoses Agent) ─────────────── print("=== Testing Diagnoses Agent ===") response = CortexAnalyst.ask( session, semantic_model="@ECDH_DB.CONSUMPTION.STAGE/diagnoses_semantic.yaml", question="Top 10 ICD-10 codes for inpatient encounters this quarter" ) print("Generated SQL:", response.sql) print(response.results.to_pandas()) # ── TEST C: Cortex Search (Clinical Documents Agent) ─────── print("=== Testing Clinical Documents Search ===") search_svc = CortexSearchService( session, service_name="ECDH_DB.CONSUMPTION.ECDH_CLINICAL_DOCS_SEARCH" ) results = search_svc.search( query="discharge summary mentioning post-surgical cardiac complications", columns=["document_content", "patient_id", "document_type"], limit=5 ) print(results) # ── TEST D: Cortex Complete (LLM response synthesis) ─────── print("=== Testing LLM Synthesis ===") answer = Complete( session, model="claude-3-5-sonnet", prompt="Summarize the top 5 ED visit trends from this data: " + response.results.to_json() ) print(answer) # ── TEST E: Simulate multi-agent orchestration ───────────── print("=== Simulating Intelligence Layer (Multi-Agent) ===") visits = CortexAnalyst.ask(session, semantic_model="@ECDH_DB.CONSUMPTION.STAGE/visits_semantic.yaml", question="Top 5 facilities by ED volume this quarter") diagnoses = CortexAnalyst.ask(session, semantic_model="@ECDH_DB.CONSUMPTION.STAGE/diagnoses_semantic.yaml", question="Top readmission diagnoses at high-volume facilities") combined = Complete(session, model="claude-3-5-sonnet", prompt=f"""You are the ECDH Intelligence agent. Synthesize these results: Visits data: {visits.results.to_json()} Diagnoses data: {diagnoses.results.to_json()} Question: What are the top readmission diagnoses at our highest-volume ED facilities? Provide a clear, executive-friendly summary.""") print(combined)
TEST E is exactly how the Intelligence Layer works. It calls multiple agents (Visits + Diagnoses), collects results, and uses an LLM to synthesize a unified answer. In Snowsight, the Cortex Agent does this automatically. In Python, you control each step and can inspect intermediate results.
Test Agents via REST API — From Any Tool

REST API Testing (curl, Postman, Any Language)

Snowflake exposes REST endpoints for Cortex Analyst and Cortex Agent. You can test from Postman, curl, or embed in any application. This is useful for CI/CD integration testing.

# ═══════════════════════════════════════════════════════════════ # Generate an auth token first (key-pair or OAuth) # ═══════════════════════════════════════════════════════════════ # Test Cortex Analyst (Visits Agent) via REST curl -X POST \ https://<org>-<account>.snowflakecomputing.com/api/v2/cortex/analyst:run \ -H "Authorization: Bearer $SF_TOKEN" \ -H "Content-Type: application/json" \ -d '{ "semantic_model": "@ECDH_DB.CONSUMPTION.STAGE/visits_semantic.yaml", "question": "How many ED visits last month by facility?", "warehouse": "ECDH_WH" }' # Test Cortex Agent (orchestrator with multiple tools) via REST curl -X POST \ https://<org>-<account>.snowflakecomputing.com/api/v2/cortex/agent:run \ -H "Authorization: Bearer $SF_TOKEN" \ -H "Content-Type: application/json" \ -d '{ "agent": "ecdh_intelligence_agent", "question": "What are the top readmission diagnoses at our highest-volume facilities?", "warehouse": "ECDH_WH" }' # Test Cortex Search (Clinical Documents) via REST curl -X POST \ https://<org>-<account>.snowflakecomputing.com/api/v2/cortex/search:query \ -H "Authorization: Bearer $SF_TOKEN" \ -H "Content-Type: application/json" \ -d '{ "service": "ECDH_DB.CONSUMPTION.ECDH_CLINICAL_DOCS_SEARCH", "query": "post-surgical complications for cardiac patients", "columns": ["document_content", "patient_id"], "limit": 5 }'

Semantic Model Development Workflow (Local)

Edit YAML Locally in VS Code

Create or modify the semantic model YAML file locally. VS Code gives you syntax highlighting and version control via Git.

Upload to Snowflake Stage

Run PUT file://./visits_semantic.yaml @ECDH_DB.CONSUMPTION.STAGE AUTO_COMPRESS=FALSE OVERWRITE=TRUE; from VS Code SQL worksheet or SnowSQL.

Test with Questions

Run SELECT * FROM TABLE(SNOWFLAKE.CORTEX.ANALYST(model => '@ECDH_DB.CONSUMPTION.STAGE/visits_semantic.yaml', question => 'your test question'));

Iterate

If the generated SQL is wrong, edit the YAML (add synonyms, adjust descriptions, add verified queries), re-upload, re-test. Full dev loop without leaving VS Code.

Commit & Deploy

Once validated, commit the YAML to Git and deploy via your CI/CD pipeline to the production stage.

Bottom line: Everything except the Snowsight chat bubble is testable from your local system. VS Code is the recommended tool for SQL-based agent testing and semantic model development. Python SDK is recommended for programmatic testing, multi-agent simulations, and CI/CD integration.
